# /diary

呼び出されたら、以下を順に行う。

## 1. 今日の作業内容を集める

- `git log --since=midnight --oneline`（または当日分のコミット）と `git status` / `git diff` で、今日行った実装・変更点を把握する。
- コミットされていない作業も対象に含める。
- 今回の会話の中で発生した詰まりどころ（エラー、設計判断で迷った点、原因調査に時間がかかった点など）を振り返る。特に詰まりがなければ正直に「特になし」と書く。捏造しない。
- TodoWriteのタスクリストや会話の流れから、次にやるべき具体的な項目を洗い出す。
- **リリース・デプロイの状態を確認する**（本番`rhing.jp`への反映は`/release`のみ。`main`へのpushでは出ない）:
  - `git fetch origin -q`のうえ`git log origin/production..main --oneline`で、`main`にあって`production`に未反映のコミット（＝本番に未リリース）を調べる。直近のタグは`git describe --tags --abbrev=0`で確認できる。
  - 今日、環境変数を必要とする変更（reCAPTCHAの`NEXT_PUBLIC_RECAPTCHA_SITE_KEY`・`RECAPTCHA_SECRET_KEY`など）を入れていたら、Vercelの環境変数に設定した証拠が会話にあるかを確認する（設定状態はgitから判定できない）。
  - 別リポジトリ（Applications/DaiDai）の変更や`firebase deploy`が絡む項目は、実行した証拠が会話にあるかを確認する。
  - 今日ユーザーがブラウザ・実機で確認したと明言した項目と、まだ確認待ちの項目を会話から分けておく。

## 2. 文書/日記.mdに追記する

- 場所: `/home/arata/Rhing/HomePage/文書/日記.md`（`文書/`ディレクトリが無ければ作成）。
- ファイルが無ければ新規作成。あれば**新しいエントリを先頭に追記**（新しい日付が上に来る形）。ただし下記のTODOリストは日付エントリより前（ファイル最上部）に置く。
- 1エントリのフォーマット:

```markdown
## YYYY-MM-DD

### 実装内容
- ...

### 詰まったところ
- ...（無ければ「特になし」）

### 次にやること
- ...
```

- 同じ日に複数回 `/diary` が呼ばれた場合は、その日のエントリに追記・統合する（同日で見出しを重複させない）。
- 内容は今日の会話・git履歴から確認できる具体的な事実のみ書く。推測や一般論で埋めない。
- 実装内容には、変更の意図・影響範囲に加え、**未リリース（`/release`待ち）・Vercel環境変数未設定・ブラウザ実機確認待ち**などの状態も明記する。
- 各日の「次にやること」は、その日の作業から見えた次の一手を書く日々のスナップショット。**過去日のエントリの「次にやること」は書き換えない**。

## 3. 最上部のTODOリストを更新する

日記の一番上（最初の`## YYYY-MM-DD`より前）に、日をまたいで持ち越す`## TODOリスト`セクションを1つだけ持つ。無ければこの時点で新規作成する。TODOリストは「日をまたいで残る唯一のバックログ」で、各日の「次にやること」とは役割が違う（両者の内容が重なるのは構わないが、削除・統合の対象になるのはTODOリストの方だけ）。

```markdown
## TODOリスト
- [ ] 項目A
- [ ] 項目B
```

更新は**丸ごと置き換えではなく、次の手順で行う**:

1. **引き継ぐ**: 既存の`## TODOリスト`にある未完了項目を全て読み出す。
2. **完了した項目を消す**: 今回の会話・git・コマンド実行の結果から**完了が確認できた項目は、行ごと削除する**（`[x]`や取り消し線で残さない）。完了の根拠になるのは、コミット・push、`/release`の実行、Vercelへの設定、ユーザーの「確認した」「できた」等の明言。**推測で消さない**。ブラウザ・実機確認のようにユーザーの確認が要る項目は、ユーザーが済んだと言うまで残す。根拠が曖昧な項目は残す。
3. **新しい項目を足す**: 次の2つを重複なく追加する（同じ内容が既にあれば足さない）。
   - TodoWriteの未完了・進行中の項目と、今回洗い出した「次にやること」。
   - リリース状態から導く項目: `origin/production`に未反映のコミットがあれば「`/release`待ち」（内容を一言添える）。`origin/production`が`main`のHEADに追いついていれば「`/release`待ち」は消す。環境変数が必要な変更でVercelへの設定証拠が無ければ「Vercelの環境変数設定が済んでいるか確認」。
4. 結果として残るのは**現時点で未完了の項目のみ**。全て完了していれば、見出しの下に項目が無い状態でよい。
5. 最終応答で、**消した項目と残した主な項目**を一言で報告する（消し過ぎの確認用）。

## 4. 文書/実装内容チェックリスト.mdを更新する

このサイト（HomePage）自身の機能の実装状況を管理するファイル。日記に書いた「今日の実装内容」との食い違いを無くす。日記・TODOの更新が済んだ直後に行い、コミットは日記と一緒に行う。DaiDaiアプリ本体のチェックリスト（`/daidaicheck`が読む別リポジトリのファイル）とは別物で、混ぜない。

- ファイルが空、または運用ルールが無い場合は、先頭に次の運用ルールを書き、セクション（トップ・団体概要・サービス紹介・daidai横丁・お問い合わせ・法務ページ・認証・インフラ等、`src/app/`の構成に沿う）と、既存のTODOリスト・日記・コードから**確認できる範囲の**現状項目を雛形として作る。
- 運用ルール（ファイル冒頭に記載しておく）:
  - `[x]`は「実装済みかつブラウザ実機で動作確認済み」のみ。コードがあっても、本番未リリース・実機未確認なら`[ ]`のまま、本文に状況（未リリース・実機確認待ち・環境変数未設定等）を注記する。
  - 一度`[x]`にした機能で、関連するバグ・不具合の修正のためコードを書き直した場合は、`[x]`を`[ ]`に戻し、直ったことを確認してから再度`[x]`にする。
  - 本当に未着手の機能の`[ ]`には4区分タグ（`**[近日]**`/`**[将来]**`/`**[検討中]**`/`**[不採用]**`）を付ける。
- 今日の実装・修正を1件ずつ見て、チェックリストに該当する項目があるか探す。
  - 既存項目に該当: 状況に合わせて`[x]`/`[ ]`と注記を更新する（今日ブラウザ確認まで済んでいなければ`[ ]`のまま「実装済み・実機確認待ち」と注記）。
  - 該当項目が無い新機能: 適切なセクションに新しい項目を追加する（動作確認前なら`[ ]`）。
  - 古くなった記述（状況が変わった項目、実装済みなのに「未実装」とある項目）があれば直す。
- 日付は日記と同じ形式で注記に入れる。推測で`[x]`にしない。ユーザーが確認したと明言した項目だけを`[x]`にする。
- 該当する変更が無い日（日記が文書のみの更新など）は、無理に書き換えず「更新なし」で次へ進む。
- 更新した場合、最終応答で何を追加・更新したかを一言で伝える。

## 5. コミット・push

文書/日記.md・文書/実装内容チェックリスト.mdおよびNext.js/Reactプロジェクト一式（`src/`, `public/`, `package.json`, `next.config.ts`, `tsconfig.json`等、リポジトリ内の変更全般）の更新は事前承認済みの操作。確認を取らずに以下を実行する。

```bash
git add -A
git commit -m "日記: YYYY-MM-DD"
git push
```

- このpushは`main`へのpushであり、本番`rhing.jp`には出ない（Vercelログイン必須のPreview URLが自動発行されるのみ）。本番反映は`/release`で明示した時だけ。
- upstreamが未設定の場合は `git push -u origin main`（または現在のブランチ）で設定する。
- **シークレットの確認（必須）**: このリポジトリはdaidai横丁関連でStripeのシークレットキーやFirebaseのサービスアカウント鍵、reCAPTCHAのシークレットキーを扱い、公開リポジトリ（`rhing-official/HomePage-Rhing`）でもある。
  1. `git add -A`の**前に**`git status`の全行を目視で確認する。次のようなファイルが一覧に出ていないか個別に確かめる: `.env*`・`service-account*.json`・`*adminsdk*.json`・`*.pem`・`*-key.json`。**`.gitignore`で除外されているのは`.env*.local`だけなので、`.env`・`.env.production`などは除外されない**点に注意。`node_modules/`・`.next/`が除外されているかも確認する。
  2. `git add -A`の**後**、コミットの前に`git diff --cached`を次のパターンで検索する: `sk_live_`・`sk_test_`・`whsec_`・`RECAPTCHA_SECRET_KEY=`・`-----BEGIN .*PRIVATE KEY-----`。（`NEXT_PUBLIC_`で始まる公開前提の値やFirebaseの`apiKey`（`AIza…`）は対象外。）
  3. 心当たりのない不審なファイルや、鍵・トークンらしき内容がヒットした場合は、**コミットせず**ユーザーに報告して指示を仰ぐ（ステージも取り消す）。
- pushが失敗した場合（コンフリクト、リモート未到達など）は、force pushなどで無理に解決せず、状況をユーザーに報告する。
